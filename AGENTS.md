# AGENTS.md

ScamWatch — a Flutter **Android** app that detects scam messages. It listens to
incoming notifications from messaging apps, runs them through an on-device Gemma
model and/or a remote backend, and raises overlay alerts. Package name is
`scamwatch_mobile_app`; Android application ID is `com.scamwatch.negavsinparis`.

## Commands

- Analyze (preferred check): `flutter analyze <path> [<path> ...]` — accepts
  multiple files/dirs. Use this to verify Dart edits.
- Run tests: `flutter test` — or a single file: `flutter test test/scam_detection_test.dart`.
- Run on device: `flutter run` (Android only in practice; other platform folders
  exist but are unused scaffolding).
- Deps: `flutter pub get` after touching `pubspec.yaml`.

## Codegen — do not hand-edit generated output

- **Localization**: `pubspec.yaml` has `generate: true`. Classes in
  `lib/l10n/app_localizations*.dart` are generated from the ARB files
  (`lib/l10n/app_*.arb`, config in `l10n.yaml`). Edit the ARB files, then
  `flutter gen-l10n` (or let `flutter run`/build regenerate). English
  (`app_en.arb`) is the template. Untranslated keys are dumped to
  `needsworktotranslate.txt`. Supported locales: en, ms, ta, zh. Do not attempt to translate unless specifically instructed to.
- **Theme**: `lib/theme/theme.dart` and its `part` files (`colors.dart`,
  `typography.dart`, `style.dart`, `icons.dart`) are generated by the Forui CLI
  (`dart forui theme create --preset fjbbdc`). Prefer regenerating over manual
  edits; customizations go in the generated function bodies.

## Architecture quirks an agent will miss

- **Two Dart entrypoints.** `main()` is the UI app. `backgroundMain()`
  (annotated `@pragma('vm:entry-point')` in `lib/main.dart`) runs in a *separate*
  `FlutterEngine` spawned natively by `ScamShieldService.kt`. It starts
  `BackgroundRunner` (`lib/background/background_runner.dart`), which owns the
  notification listener and model loop. Code that must run in the background
  belongs on that path, not in the widget tree.
- **Dart ↔ Kotlin bridge** uses `MethodChannel`/`EventChannel` names defined in
  `lib/services/scamshield_channels.dart`: `scamshield/native` (Dart→native:
  overlay alerts, wake locks, status), `scamshield/control` (native→Dart),
  `scamshield/ui`, `scamshield/storage`, and the `scamshield/notifications`
  event stream. The native side lives in
  `android/app/src/main/kotlin/com/scamwatch/negavsinparis/` — keep channel
  names in sync across both languages.
- **Scam evaluation routing.** `lib/services/evaluation_router.dart` runs the
  on-device model first and escalates to the remote API only when the local
  verdict is low-confidence; `forceCloud` inverts this (cloud first, local
  fallback). Model verdicts are JSON parsed by `parseScamVerdict`
  (`lib/core/scam_verdict.dart`) — the model prompt is in `lib/core/scam_prompt.dart`.
- **Backend contract** is documented in `API.docs.md` and is the source of truth
  for the HTTP client in `lib/api/`. All IDs are opaque strings, bodies are
  `snake_case`, routes are under `/api/v1`. The base URL in
  `lib/api/api_config.dart` is a **temporary ngrok tunnel** that changes — don't
  treat it as stable.

## Conventions

- `lib/` layout: `api/` (HTTP client), `background/` (headless engine),
  `core/` (models/prompts/catalog), `services/` (evaluators, channels, settings,
  logs), `state/` (ChangeNotifier controllers), `screens/`, `widgets/`, `theme/`.
- State uses `provider` with `ChangeNotifier` controllers wired in `main.dart`.
- Imports use the `package:scamwatch_mobile_app/...` form, not relative paths, in
  app-level code.
- Only write tests for logic you're not confident in (e.g. verdict parsing,
  routing). Skip tests for trivial changes. Existing tests live in `test/` and
  use fake `ScamEvaluator` implementations rather than real models/network.
